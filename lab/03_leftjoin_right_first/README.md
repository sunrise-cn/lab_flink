# 实验 03：LEFT JOIN 右流先到、左流后到，还能匹配上吗？

## 1. 实验目的

沿用统一背景（订单流 × 订单属性流，见根 `README.md`）。真实场景中订单属性可能**先于**订单到达（供应商系统先推送了属性，订单主事件后到）。

验证问题：LEFT JOIN 右流先到、左流后到，还能匹配上吗？分两种情况对比：

1. **普通 LEFT JOIN**：不加时间窗口，双侧状态默认永久保留
2. **LEFT JOIN + 前后 1 分钟事件时间窗口**（interval join）：双侧状态按窗口保留

两种情况的表现一致吗？（用"左流晚到 30s（窗口内）"和"左流晚到 2min（超窗口）"两组对照验证）

## 2. 实验过程

### 2.1 环境

本机 docker compose 平台：Kafka 3.9.1（KRaft 单节点）+ Flink 2.2.1（1 JM + 1 TM），checkpoint 周期 10s（upsert-kafka 按 checkpoint 批量写出）。

### 2.2 实验设计

订单流、订单属性流各用独立 source topic，均以业务时间字段定义事件时间和水位线（`WATERMARK ... - INTERVAL '5' SECOND`，允许 5s 乱序）。两条 join 分支（join 条件 `o.za_order_no = p.za_order_no`，interval 分支另加 `o.apply_ts BETWEEN p.hyfw_ts ± INTERVAL '1' MINUTE`）各写一个独立的 upsert-kafka sink，合并为同一个 STATEMENT SET 作业。完整 SQL 见 `demo.sql`。

### 2.3 测试数据与步骤

6 条消息按顺序发送，相邻间隔 15s（> checkpoint 周期 10s，保证每步的效果独立落盘）：

```
步骤0  → props  T001 hyfw 10:00:00   组1：属性先到
步骤1  → order  T001 apply 10:00:30  组1：订单晚 30s（在 ±1min 窗口内）
步骤2  → props  T002 hyfw 11:00:00   组2：属性先到
步骤3  → order  T002 apply 11:02:00  组2：订单晚 2min（超出 ±1min 窗口）
步骤4  → props  T999 hyfw 11:04:00   收尾：推进属性流水位线
步骤5  → order  T999 apply 11:04:30  收尾：推进订单流水位线（与 T999 属性互配，兼作对照）
```

步骤4/5 的作用：interval LEFT JOIN 的未匹配 null 补齐行要等**水位线越过该行的窗口右边界**（T002 为 11:03:00）才输出；而双输入算子的水位线取两侧最小值，所以两条流都要各发一条晚事件把水位线推过 11:03:00。

复现命令（在项目根目录执行，可反复执行，每次都从干净状态开始）：

```bash
./lab/03_leftjoin_right_first/run.sh    # 一键复现：建 topic → 取消本实验旧作业 → 清空 source/sink topic → 提交 SQL → 发消息 → 验证
```

### 2.4 实际观察结果（sink topic，格式 `key <= value`）

普通 LEFT JOIN（`03_leftjoin_right_first_regular_sink`），共 **3 条，全部匹配，无 null 行、无墓碑**：

```
(T001, 10:00:30, 10:00:00)  <=  正常消息   ← 步骤1：属性先到，订单晚 30s，匹配上
(T002, 11:02:00, 11:00:00)  <=  正常消息   ← 步骤3：订单晚 2min，照样匹配（无时间边界）
(T999, 11:04:30, 11:04:00)  <=  正常消息   ← 步骤5：收尾对照组，匹配
```

LEFT JOIN + 前后 1min 窗口（`03_leftjoin_right_first_interval_sink`），共 **3 条 = 2 条匹配 + 1 条延迟 null 补齐行**：

```
(T001, 10:00:30, 10:00:00)  <=  正常消息   ← 步骤1：订单晚 30s 在窗口内，匹配上（与普通 join 一致）
(T999, 11:04:30, 11:04:00)  <=  正常消息   ← 步骤5：收尾对照组，匹配
(T002, 11:02:00, EMPTY)     <=  正常消息   ← 步骤5 才落盘：订单晚 2min 超窗口，不匹配；
                                             且 null 行延迟到水位线过 11:03:00 才输出
```

注意 T002 的 `EMPTY` 行在消费结果中排在步骤5 的 T999 之后——它确实是在水位线被步骤4/5 推过窗口右边界后才发出的，不是步骤3 到达时立即输出的。

## 3. 实验结论

**右流先到、左流后到，两种 LEFT JOIN 都能匹配上**——但两者的匹配能力并不完全一致：

| | 普通 LEFT JOIN | LEFT JOIN + ±1min 窗口 |
|:--|:--|:--|
| 左流晚到 30s（窗口内） | 匹配 | 匹配（一致） |
| 左流晚到 2min（超窗口） | **照样匹配**（状态永久保留） | **不匹配**，输出 null 补齐行 |
| 未匹配 null 行的输出时机 | 左流到达立即输出 | **延迟**到水位线越过窗口右边界才输出 |

机制解读：

1. 普通流式 join 把右流全部历史保留在状态里（默认永久），右流先到的数据会一直等，左流任何时刻到达都能命中——所以"右到左后"和"左到右后"对称，都能匹配。
2. interval join 的状态按窗口保留：右流只等"自己时间 ±1 分钟"内的左流，左流晚到超过窗口右边界时右流状态已被清理（或本就不在匹配区间），于是不匹配并转为输出 null 补齐行。
3. interval LEFT JOIN 的 null 补齐行是**延迟确定**的：只有水位线越过"该左行可能匹配的最晚右流时间"（T002 = 11:02:00 + 1min = 11:03:00），引擎才能断定不会再有匹配，才输出 null 行。双输入算子水位线取两侧最小值，复现造数时两条流都要发晚事件推进水位线。
4. 与实验 01/02 的另一个对照：右流先到时两种 join 都**没有** null 补齐行和回撤墓碑（右流到达不产生输出，左流到达直接命中）；null 行只出现在"左流先到等右流"（实验 01）或"超窗不匹配"（本实验组2）的场景。
5. 工程推论：用 interval join 可以对 join 状态保留时长兜底（避免普通 join 状态无限增长），代价是超窗晚到的数据匹配不上、且未匹配行的输出有窗口+水位线量级的延迟。
