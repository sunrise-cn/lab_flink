# 实验 04：水位线（watermark）在 window 和 join 中的作用

## 1. 实验目的

理解 watermark 到底控制什么。核心困惑：**为什么有些结果"数据明明到了却不输出"，要等后续一条不相干的消息来"推一把"才出现？**

本实验用分阶段发消息 + 每阶段消费 sink 的方式，直接观察"结果什么时候才落盘"，验证：

1. 事件时间**窗口**的聚合结果，要等水位线越过窗口结束时间才输出
2. interval join **匹配成功**的行立即输出，不等水位线
3. interval LEFT JOIN **未匹配的 null 补齐行**，要等水位线越过该行的窗口右边界才输出
4. **双输入算子**（join）的水位线取两侧输入的最小值：只推一条流的水位线，另一条不动，算子水位线就不动

## 2. 实验过程

### 2.1 环境

本机 docker compose 平台：Kafka 3.9.1（KRaft 单节点）+ Flink 2.2.1（1 JM + 1 TM），checkpoint 周期 10s（upsert-kafka 按 checkpoint 批量写出）。

### 2.2 实验设计

订单流、订单属性流各自定义事件时间和水位线（`WATERMARK ... AS ts - INTERVAL '5' SECOND`，即水位线 = 已见最大事件时间 - 5s）。一个作业两条分支（完整 SQL 见 `demo.sql`）：

- **窗口分支**：订单流 1 分钟滚动窗口计数 → `window_sink`
- **join 分支**：订单 LEFT JOIN 订单属性（±1min 事件时间窗口）→ `join_sink`

先记住一句话：**水位线是引擎对"事件时间已经进展到哪"的估计，含义是"相信不会再看到比它更早的事件了"**。凡是要等"确定不会再变"才能输出的结果，都由水位线放行。

### 2.3 测试数据与步骤

8 条消息分 6 个阶段发送，每阶段发完等 15s（> checkpoint 周期 10s）让 sink 落盘，然后消费观察（`run.sh` 自动执行）：

```
阶段1  → order  T001 10:00:10, T002 10:00:40   同一窗口 [10:00,10:01)，发完订单流水位线=10:00:35
阶段2  → order  T003 10:02:00                  订单流水位线推到 10:01:55，越过 10:01:00
阶段3  → props  T101 10:10:20 + order T101 10:10:50   join 匹配组（属性先到，订单晚 30s）
阶段4  → order  T102 10:20:00, T103 10:22:00   T102 无属性；T103 只推订单流水位线（10:21:55）
阶段5  → props  T999 10:24:00                  推属性流水位线（10:23:55）
阶段6  → order  T999 10:24:30                  与 T999 属性互配；订单流水位线推到 10:24:25
```

复现命令（在项目根目录执行，可反复执行，每次都从干净状态开始）：

```bash
./lab/04_watermark_window_join/run.sh                # 一键复现（分阶段发消息 + 逐阶段消费观察）
./lab/04_watermark_window_join/send-messages.sh      # 也可不分阶段，一次发完全部 8 条
```

### 2.4 实际观察结果（逐阶段消费 sink）

**阶段 1**：窗口数据已到齐（T001、T002 都在窗口 [10:00,10:01)），但 window_sink **一条都没有**——水位线 10:00:35 还没越过窗口结束时间 10:01:00，窗口没关门：

```
Processed a total of 0 messages
```

**阶段 2**：T003（事件时间 10:02:00）并不属于这个窗口，但它把水位线推到 10:01:55 > 10:01:00，窗口立刻关门输出：

```
{"window_start":"2026-08-13 10:00:00"}  <=  {...,"window_end":"2026-08-13 10:01:00","order_cnt":2}
Processed a total of 1 messages
```

**阶段 3**：join_sink 里 T101 **匹配行立即出现**（订单一到就配对，不等水位线）；同时 T001/T002/T003 的 `EMPTY` 补齐行也出现了——它们是没有属性的订单，null 行一直憋到"两条流的水位线都越过各自窗口右边界"才放行（此刻算子水位线 = min(10:10:45, 10:10:15) = 10:10:15）：

```
(T001, 10:00:10, EMPTY)  <=  ...     ← 等算子水位线 > 10:01:10，此刻才放行
(T002, 10:00:40, EMPTY)  <=  ...     ← 等 > 10:01:40，此刻才放行
(T101, 10:10:50, 10:10:20)  <=  ...  ← 匹配成功，立即输出（10:10:50 在 10:10:20±1min 内）
(T003, 10:02:00, EMPTY)  <=  ...     ← 等 > 10:03:00，此刻才放行
Processed a total of 4 messages
```

**阶段 4**（关键对照）：T102 无属性（null 行需算子水位线 > 10:21:00）；T103 把**订单流**水位线推到 10:21:55——但 join_sink **纹丝不动，还是那 4 条**！因为属性流水位线还停在 10:10:15，双输入算子取最小值 = 10:10:15，没过 10:21:00：

```
Processed a total of 4 messages   ← T102 的 EMPTY 行没有出现
```

**阶段 5**：只发了一条属性 T999（10:24:00），把**属性流**水位线推到 10:23:55；算子水位线 = min(10:21:55, 10:23:55) = 10:21:55 > 10:21:00，T102 的 `EMPTY` 行立刻出现：

```
...(原 4 条)
(T102, 10:20:00, EMPTY)  <=  ...     ← 属性流水位线被推高后才放行
Processed a total of 5 messages
```

**阶段 6**：T999 订单与 T999 属性互配（立即输出）；订单流水位线推到 10:24:25，算子水位线 = min(10:24:25, 10:23:55) = 10:23:55 > 10:23:00，T103 的 `EMPTY` 行放行：

```
...(原 5 条)
(T999, 10:24:30, 10:24:00)  <=  ...  ← 匹配成功，立即输出
(T103, 10:22:00, EMPTY)  <=  ...     ← 等算子水位线 > 10:23:00，此刻才放行
Processed a total of 7 messages
```

**最终 window_sink 全量**：5 个窗口——`[10:00,10:01)×2`、`[10:02,10:03)×1`、`[10:10,10:11)×1`、`[10:20,10:21)×1`、`[10:22,10:23)×1`。注意 **T999 订单所在的 [10:24,10:25) 窗口永远缺席**：之后没有任何事件把水位线推过 10:25:00，这个窗口永远不会关门。

## 3. 实验结论

**水位线是引擎的"事件时间进度表"：watermark = 已见最大事件时间 - 允许的乱序（本实验 5s），语义是"相信不会再有比它更早的事件"。所有需要"确定不会再变"才能输出的结果，都等水位线放行。**

| 场景 | 谁控制输出时机 | 实测表现 |
|:--|:--|:--|
| 窗口聚合 | 水位线 > 窗口结束时间才输出 | 阶段1 数据到齐但 sink 为空；阶段2 水位线一过立即出现 |
| join 匹配成功 | **不等水位线**，记录到了就配对输出 | 阶段3/6 匹配行立即出现 |
| join 未匹配 null 补齐行 | 水位线 > 该行窗口右边界才输出（此前引擎不敢断言"没匹配上"） | T102 在阶段4 憋住、阶段5 才放；T103 阶段6 才放 |
| 双输入算子（join） | 算子水位线 = **两侧输入水位线的最小值** | 阶段4 只推订单流无效；阶段5 推属性流才放行 |
| 流停了 | 水位线停摆，挂着的结果永远不出 | [10:24,10:25) 窗口在 sink 中永远缺席 |

要点解读：

1. **窗口为什么"数据到了不出结果"**：窗口结果要"定稿"才能发——只要水位线还没过窗口结束时间，理论上就还可能有属于这个窗口的迟到数据，引擎不能提前输出一个还会变的数。所以窗口输出永远滞后于数据，滞后量 = 窗口长度 + 乱序容忍 + 下一条事件的到来时机。
2. **join 匹配为什么不等水位线**：配对是两批已到场状态的即时计算，结果只增不改（regular/interval join 的匹配行是 append 的），没有"定稿"问题，所以立即输出。
3. **null 补齐行为什么要等水位线**：LEFT JOIN 输出 null 行 = 引擎断言"这个左行在窗口内没有右行可配"。事件时间乱序下，右行可能迟到，引擎只有等水位线越过"该左行可能匹配的最晚右流时间"（窗口右边界），才敢下这个结论。**延迟量不确定**——它取决于后续事件什么时候来（阶段4 憋了约 1 分钟墙钟时间），流停了甚至永远不来。
4. **生产含义**：事件时间窗口/interval join 的结果时效性，取决于**所有输入流**持续推进水位线。某条流长时间不来数据（或空闲分区），水位线就卡住，窗口结果和未匹配 null 行都会积压——这就是为什么需要 watermark 空闲检测（`table.exec.source.idle-timeout`）或多流都要保活。
